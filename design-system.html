Mixup — Introducing design
into a dev-only team.

Before my involvement, there was no designer on the team. Developers were building the interface directly in code — no documentation, no shared components, no visual language.

The first job wasn't designing components. It was establishing why a design system mattered and how the team would work with it. Adoption isn't guaranteed when a team has never worked with a designer — you have to show the value quickly, on real features, before the system becomes a habit.

Approach

Primitive tokens before anything else — color palette, spacing, typography, radius, shadows. These became the contract between design and code. Once agreed on, every component built on top was automatically consistent.

The UI Kit grew alongside the product. Mixup's dark, studio-inspired aesthetic required very custom components — waveform players, version lists, timestamped comment threads. None of these exist in standard libraries. Building on Tailwind tokens meant bespoke components stayed coherent with the rest of the system.

Buttons & states

Impact

  • Devs could rely on design documentation for the first time
  • Consistent visual language from day one
  • Same token language between design and code — no more "it's almost the same color"
  • New features built faster as the component library grew

Puremix — Rebuilding when
debt is too heavy to patch.

The existing codebase was too fragile to build on — any change risked breaking something else. The technical debt wasn't just cosmetic; it ran deep into the architecture. Patching would have been slower and riskier than rebuilding.

There was no dedicated design system team. Verification happened in pre-prod and post-prod — not in design reviews. In parallel, I recruited student designers: I was onboarding and mentoring them while relying on them for reviews. More eyes on the product, but more time spent aligning on standards.

At the time, tooling didn't support native token management. The process was explicit by necessity — tokens documented manually, Tailwind config written to match exactly. That discipline forced better conversations between design and dev than any tool would have.

"For the first time, what shipped looked like what was designed. Not approximately — exactly."

Typography scale

Impact

  • First full design/code alignment in the product's history
  • Fewer "that's not what I designed" moments in QA
  • New pages assembled from existing components rather than designed from scratch
  • Student designers trained on real product work

Spacefill — Migrating without
breaking production.

A live B2B SaaS with active users, running on an abandoned library. The product couldn't stop shipping while we migrated. This is the hardest design system scenario — you can't start fresh, you can't leave things as they are.

3-phase migration

01
Primitive tokens

Color primitives → semantic tokens, spacing scale, typography. Nothing visible to users yet — but the design/code contract is now in place.

02
Base components

Buttons, inputs, badges, tables, modals. Built once on the new token system. Existing components left in place until their page is migrated.

03
Page by page migration

Stock page, Order page, Transportation... Each sprint, one page. Every component replaced with the new system. No big bang, no regression.

Spacefill's logistics domain has very specific needs — multi-unit input forms, hierarchical stock tables, order status flows. The system needed clear rules for extension: when to create a new component, how to name it, how to keep harmony with the base system.

"The goal wasn't to replace everything. It was to make sure that whatever existed — old or new — felt like it belonged to the same product."

Breakpoint system

Impact

  • Outdated library fully replaced without service interruption
  • New features built faster on a stable, maintained foundation
  • Visual consistency restored across all pages
  • Domain-specific components documented and reusable

Takeaways

A design system is a product for your team.

It has users, adoption challenges, and a roadmap. Treating it as a deliverable rather than a living system is the fastest way to end up with an outdated library nobody uses.

Tokens first, always.

Whether starting from scratch or migrating, the token layer comes before any component. It's the cheapest thing to get right early — and the most expensive to fix later.

Introducing design into a dev-only team is its own challenge.

Adoption isn't guaranteed. You have to demonstrate value on real features before the system becomes a habit.

Tooling matters less than discipline.

We built coherent systems before native token support existed in design tools. The manual process forced better conversations — conversations that better tooling can accelerate but not replace.

Extension rules are as important as the components.

Any system will face edge cases. The question isn't whether you'll need custom components — it's whether you have clear rules for creating them without breaking the harmony.
